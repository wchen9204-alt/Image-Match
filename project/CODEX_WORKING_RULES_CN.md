# Codex 工作规则

本文件用于约束 Codex 在 `D:\Experimental-testing-platform` 项目中的默认工作方式。

目标：
- 保持代码、配置、注释风格稳定。
- 减少来回重复说明同一类要求。
- 在新增实现、修复问题、调整配置时，优先遵守本文档。

## 使用方式

每次在本项目中开始新的实现、修复、重构、配置修改前，应先阅读本文件，再执行具体任务。

如果用户的当次指令与本文件冲突：
- 以用户最新、最明确的指令为准。
- 若不冲突，则默认继续遵守本文件。

## 默认沟通语言

- 默认使用中文和用户沟通。
- 代码、接口名、配置字段、命令输出和报错信息可以保留英文原文，但解释应使用中文。
- 如果用户明显不是开发者，说明问题和结果时应尽量使用简单语言，减少不必要的术语。

## 默认工作流程

收到任务后，默认按以下顺序推进：

1. 先理解目标，再查看项目结构、相关配置和相关源码，不先凭记忆猜测实现。
2. 判断任务类型：功能开发、Bug 修复、配置调整、界面修改、文档整理或验证分析。
3. 优先做最小必要改动，保持现有项目风格，不修改无关文件。
4. 如果改动涉及前后端契约、共享数据结构、配置字段或跨模块调用，必须同步检查类型、接口字段和调用方。
5. 配置优先放在配置文件中；除非确有必要，不把可配置行为硬编码到业务代码里。
6. 完成后做与任务风险相匹配的验证；如果无法验证，最终汇报中必须说明原因。

必要时可以参考开源项目或创建 subagent 辅助分析，但应保持改动边界清晰，并说明引入参考或辅助分析的用途。

## 任务收尾与复盘

每次任务完成后，应做一次简短复盘。

如果本次任务暴露出“可重复发生、可写成规则、下次能避免”的项目内问题：
- 优先记录到当前项目的 `LESSONS.md`。
- 如果同类问题重复出现两次以上，或明显属于本项目高频坑，再整理进当前项目的规则文档。
- 只有跨多个项目都成立的稳定规则，才适合进入全局规则。

不要记录一次性偶发问题、临时网络波动、与当前项目无关的泛泛感想，或和已有规则重复的内容。

## 最终汇报要求

最终汇报默认包含以下信息，并根据任务大小压缩表述：

- 改了什么。
- 为什么这样改。
- 影响范围。
- 实际执行了哪些验证命令或检查。
- 未完成项、残余风险，或明确说明没有运行测试。
- 如果用户下一步需要手动操作，应写清楚具体操作。

## 规则

### 1. YAML 配置规则

- YAML 参数应尽量补充中文注释。
- YAML 参数注释中应尽量写明：
  - 默认值
  - 可选项
  - 参数作用
- 如果某个参数只有在特定方法下生效，应在注释中说明适用范围。
- 如果某个参数已不是主路径使用，但仍作为兼容回退保留，也应明确说明。

示例要求：
- `match_mode` 要注明可选项，如 `KNN / MATCH / RADIUS`
- `descriptor` 要注明可选项，如 `HU / MATCH_SHAPES / SHAPE_CONTEXT / FD / EFD`
- 几何模型、初始化方式、检索模式、近似模式等枚举型参数，都应尽量写清可选项

### 2. 注释语言规则

- 默认使用中文注释。
- 新增注释优先使用简洁、明确、工程化的中文表达。
- 除非第三方接口、日志关键字、专有名词必须保留英文，否则注释优先中文。

### 3. 类与函数注释规则

- 新增类时，应注释类的功能和用途。
- 新增重要成员变量时，应注释其含义，尤其是非显然参数、阈值、状态变量。
- 新增函数时，应在函数实现处注释函数功能；如果头文件已有声明注释，实现处仍应补充与实现职责相关的简洁说明。
- 核心函数必须有步骤注释：如果函数逻辑较长、步骤较多，或者包含关键判断、几何筛选、回退路径、映射关系、特殊兼容逻辑，应在关键步骤前添加编号式或阶段式中文注释。
- 其它非核心函数不要求逐行解释，但重要步骤、关键分支、资源申请/释放、外部进程调用、路径解析、数据格式转换、异常回退等位置也应添加简洁中文注释。
- 对包含多个关键处理阶段的函数，除函数功能注释外，还应在关键语句前补“这一句在做什么/为什么这样做”的步骤注释，例如缩放、变换、筛选、优化、写回结果等。
- 注释应解释“为什么这样做”或“这一段在流程中的作用”，避免无信息量的空话式注释。

优先需要注释的情况：
- 描述子计算
- 几何一致性筛选
- 回退策略
- 索引映射
- 可视化逻辑
- 兼容旧配置/旧路径的分支

### 4. 保护已有注释

- 不要随意删除已有注释。
- 如果已有注释内容仍然有效，应保留。
- 如果已有注释表达不清、存在乱码、或与当前实现不一致，应优先修正，而不是直接删除。
- 如果必须替换旧注释，应保证新注释至少提供同等或更高的信息量。

### 5. 修改范围控制

- 优先做最小必要修改。
- 不因为顺手而大范围改名、重排、清空注释、统一格式。
- 配置、注释、实现修改应尽量围绕当前任务展开，不扩散到无关模块。

### 6. 通用性与可扩展性规则

- 避免硬编码单一方法、单一文件路径、单一输出目录、单一指标读取来源或单一数据结构。
- 当多个方法族（如点特征法、结构法、直接法）需要共享评估、可视化、输出或几何估计逻辑时，应优先抽象统一访问层或接口。
- 新增方法、指标、可视化输出或配置类型时，应尽量通过枚举、工厂、配置项、统一数据视图或策略分支扩展，而不是在调用处散落 `if/else` 特判。
- 对必须保留的兼容回退、旧字段读取、方法别名映射，应集中封装并添加中文注释说明原因。
- 入口类、命令行入口、应用层主流程文件应尽量保持“流程编排型”结构：负责识别运行模式、加载配置、组织执行和汇总结果，不应长期堆叠具体解析、配置覆盖、摘要生成、CSV 写入、可视化输出等细节实现。
- 当某段逻辑可以被清晰命名，或会被多处复用时，应优先抽取为私有 helper 函数、独立 helper 模块、writer、serializer 或 generator，使主流程只保留高层调用关系。
- 配置覆盖逻辑（如 compare YAML 覆盖 pipeline YAML 的 `visualization`、`output_dir`、`name` 等字段）应集中封装到统一辅助函数中，避免在主流程中散落硬编码赋值。
- 抽取 helper/module 时，必须同步删除原位置的重复实现；不要只新增文件和函数却保留旧代码，避免职责重复、维护分裂或潜在重定义。
- helper/module 的命名应体现职责边界，例如 `registration_app_helpers` 负责应用层配置装配和摘要辅助，`summary_csv_writer` 负责 CSV schema 与写出。
- 如果暂时只能写局部特判，应说明适用范围和后续可扩展方向，避免让临时代码成为默认架构。
- 不要为了复用旧流程而把一个方法族的数据伪装成另一个方法族的数据；应优先建立明确的数据转换或只读视图。

### 7. 结果验证

- 修改代码后，若条件允许，应进行编译或最小验证。
- 如果只修改 YAML 注释或文档，也应确认未破坏格式。
- 如果无法验证，应明确说明未验证的原因。

## 默认执行检查清单

开始修改前，默认检查以下事项：

1. 本次是否会改 YAML？
   - 若会，补默认值与可选项注释。
2. 本次是否会新增/修改类或函数？
   - 若会，补中文功能注释与关键步骤注释。
3. 本次是否会触碰已有注释？
   - 若会，优先保留并修正，不随意删除。
4. 本次是否存在硬编码或只适用于单一方法族的读取/分发逻辑？
   - 若存在，优先改为统一接口、工厂、配置项、枚举映射或只读数据视图。
5. 本次是否让入口文件、应用层主流程或核心调度函数堆叠了可独立命名的实现细节？
   - 若存在，优先抽取为 helper、writer、serializer、generator 或专门模块，并同步删除原位置重复实现。
6. 本次是否新增、删除、移动或重命名目录/文件/模块/方法族/配置目录？
   - 若会，检查并同步维护项目结构相关文档。
7. 本次修改后是否可以编译或最小验证？
   - 若可以，执行验证。

## 当前项目中的特别约定

- 结构法、轮廓法、直线法中的方法分层要尽量清晰。
- 轮廓级描述子、响应图配准、几何估计不要混淆层级。
- 对参数语义容易混淆的 YAML，优先用注释写清“这是描述子参数 / 这是响应图参数 / 这是几何参数”。
- 如果新增、删除、移动或重命名项目目录、源文件、头文件、配置目录、方法族、pipeline 或重要模块，应同步维护项目结构和说明文档，至少检查：
  - `PROJECT_DIRECTORY_STRUCTURE_CN.md`
