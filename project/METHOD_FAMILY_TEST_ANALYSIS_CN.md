### 现在怎么验

点特征法这条线上，最近新增了两个 warp 验证项：

- `min_containment`
  - 看 warped source 与 target 的前景交集，占两张图较小前景面积的比例。
  - 它主要解决的是“一张图可能是另一张图局部”时，整图式重叠判断不合适的问题。
- `min_bidirectional_coverage`
  - 同时看 `source coverage` 和 `target coverage`，再取两者较大值作为最终 coverage。
  - 它主要解决的是局部图场景下，应该允许“至少一个方向基本完整保留”，同时继续拦住那种“只贴上一小块局部区域就被误判通过”的错误解。

目前这条线实际在用的验证项先记这几类：

1. `match_quality`
   - 看 `num_inliers`、`inlier_ratio`、`mean_reproj_error`。
2. `warp_overlap.min_containment`
   - 看 warped source 与 target 的前景局部包含率。
3. `warp_overlap.min_bidirectional_coverage`
   - 看 `max(source_coverage, target_coverage)` 是否达到阈值。
4. `photometric.max_nmad`
   - 看 warp 后的光度误差是否超阈值。

其中 `min_bidirectional_coverage` 和各项具体怎么算、怎么算前景 mask，详细定义放在 `PROJECT_PIPELINE_INTERNALS_CN.md`；这份分析文先只记“加了什么”和“现在用哪些验证项”。

### 过滤方法现状

当前工程里已经实现并实际尝试过的点特征过滤方法主要有：
- `ratio_test`
- `cross_check`
- `distance_distribution`
- `distance_threshold`
- `min_distance`
- `gms`
- `pairwise_rigid_consistency`

其中 `pairwise_rigid_consistency` 是最近新增的一项点特征预过滤，位置在 `matcher` 之后、`rigid_estimator` 之前。它不是几何估计器，而是先用刚体一致性把一部分明显不合理的错配压掉，再把剩余 matches 送进 rigid 求解。

当前第一版实现采用的是“`pairwise vote + 主旋转峰`”：
1. 从当前 `filtered_matches` 中读取有效点对。
2. 两两组成 match pair，先过滤掉 pair 距离过近的组合。
3. 比较 source pair 与 target pair 的长度差，只保留长度接近的 pair。
4. 计算每个 pair 的相对旋转角，并投票到旋转直方图。
5. 取票数最高的主旋转峰，作为当前场景的主导旋转候选。
6. 重新统计每个 match 被多少个“接近主旋转峰”的 pair 支持。
7. 仅保留支持票数达到阈值的 matches，再交给 `rigid_estimator`。

这项过滤的目标，是尽量贴合当前这类场景假设：
- 主要是平移 + 旋转。
- 场景静态。
- 无明显光照变化。
- 不考虑缩放。

它主要想解决的是：在弱纹理、长方形前景、局部重叠这类样本里，普通描述子匹配容易保留一批“局部上看着像，但整体不满足 rigid 几何”的错误点。`pairwise_rigid_consistency` 先做一轮刚体关系筛选，能在进入 RANSAC / rigid 精修前提前压掉其中一部分。

现阶段已经可以记一个更新后的明确结论：**当前点特征主线里，`pairwise_rigid_consistency` 和基于 filtered matches 的 rigid 候选生成都已经确认是有效改动**。

先分别记它们为什么有作用。

1. `pairwise_rigid_consistency` 为什么有作用
- 它起作用的位置在 `matcher` 之后、`rigid_estimator` 之前，属于“几何前预过滤”。
- 它不是靠单个点的描述子距离做判断，而是看“点对之间的相对长度和相对旋转是否能互相支持”。
- 这正好能压掉一类当前最麻烦的错配：单看局部纹理像是对的，但放到 rigid 几何关系里彼此不一致。
- 对当前场景尤其有效的原因是：
  - 当前假设本来就是平移 + 旋转、静态、无明显光照变化、不考虑缩放。
  - 在这个假设下，真正正确的 matches 往往会在相对旋转上形成一个主峰，而错配更容易分散。
  - 所以 `pairwise vote + 主旋转峰` 可以先把“能共同支持同一刚体方向”的点留下来，把大量互相打架的点排掉。
- 它的实际价值，不只是“减少匹配数量”，而是提高进入 RANSAC 的候选纯度。候选纯度一旦提高，后面的 rigid 初值、内点集和精修稳定性都会跟着变好。
- 结合目前人工验证，可以认为它对 `Test04` 这类样本已经不是“偶然改善”，而是确实在起正作用。

2. 多候选 rigid 为什么有作用
- 它起作用的位置在 `rigid_estimator` 内部，属于“几何阶段的候选补救”。
- baseline 仍然保留当前 RANSAC rigid 结果，但不再只相信这一个结果，而是从过滤后的 matches 里额外生成多组严格 rigid 候选，再统一评分选最好的一组。
- 这一步有效，核心是因为当前不少失败样本不是“完全没有正确对应”，而是“正确对应只占一小部分，单次 RANSAC 很容易先抓住一个局部最优”。
- 尤其是下面这几类情况，多候选会明显更重要：
  - 长方形前景、边界重复、弱纹理。
  - 一张图只是另一张图的局部。
  - 存在 `180` 度旋转歧义，错误方向的局部区域也能解释一小撮点。
- 在这些场景里，单个最优内点模型未必是真正全局更对的模型，它可能只是“先解释了某一小块局部”。多候选的价值就是把这些局部可行模型都拿出来，再通过后续评分把更像真实配准的那一个挑出来。
- 所以它起作用的方式不是“替代 RANSAC”，而是避免流程过早锁死在某一个局部最优上。

3. 为什么这两个会叠加起作用
- `pairwise_rigid_consistency` 先解决“进入几何前候选太脏”的问题。
- 多候选 rigid 再解决“即使候选已经变干净，单次求解仍可能卡在局部最优”的问题。
- 前者更像是在提升输入质量，后者更像是在提升求解阶段的容错和搜索能力。
- 两者叠加之后，当前点特征法的成功率提升就比较符合现象：不是只靠一个阈值放松，而是前端过滤和后端选模都变得更贴近 rigid 场景本身。

不过也要把边界记清楚：这并不表示问题已经彻底解决。已经看到的现象大致还是这样：
- `MATCH` 直接匹配在一些样本上反而比 `KNN + ratio_test` 更稳。
- 一旦切到 `KNN`，很多样本虽然候选数变了，但最终几何结果并没有明显变好。
- 有些过滤方法筛完之后，`filtered_matches` 仍然和 `raw_matches` 很接近，说明它们没有有效压掉坏匹配。
- 也有一些方法会把候选压得太狠，导致后面 RANSAC / rigid 阶段可用内点更少。
- `gms` 这类更强调空间一致性的过滤，当前实现虽然已接入，但暂时也没有表现出稳定优于现配置的效果。
- `pairwise_rigid_consistency` 和基于 filtered matches 的 rigid 候选生成虽然都已经确认有效，但对 `Test05/06` 这类更强歧义样本仍然没有完全兜住，说明这两步解决的是主要矛盾，不是全部矛盾。

所以目前对过滤这一块的判断应该是：
- 当前最值得保留的默认组合，是 `pairwise_rigid_consistency + 基于 filtered matches 的 rigid 候选生成` 这一前后配合方案。
- 现在的瓶颈仍然是“错配压不干净”和“压完之后有效对应又不够多”这两个矛盾同时存在。
- 后面还需要继续补更强的判别能力，尤其要继续针对 `180` 度旋转歧义、弱纹理和局部最优问题。

另外还要记住：即使后面找到了更强的过滤方法，它也未必能单独解决 `Test04`、`Test06` 这类样本。因为这两个样本的问题不只是“坏匹配太多”，还可能包含“`180` 度旋转歧义下，错误方向的局部重合也能骗过当前流程”。

### 历史参考：SIFT

`project/outputs/batch/keypoint/sift_pipeline/summary.csv` 仍然有参考价值，但现在只能作为旧批次记录，不应再拿它代表当前主线结果。

SIFT 这条线上之前已经确认过几件事：
- `Test01/04/05/06` 的主要失败点都集中在 rigid 阶段，典型报错是 `failed to refine rigid transform from RANSAC inliers`。
- 之前调过 `MATCH`、`KNN`、`ratio_test`、`cross_check` 后，能确认 filter 不是完全没执行，但对这些坏样本的改善有限。
- 问题核心更像是：进入几何的候选里仍然有较多错配，或者当前对应关系更支持带统一缩放的 similarity / partial affine，而不是严格 rigid。

所以现在对 SIFT 的判断先保留为：
- 不是单纯 norm 配置问题。
- 不是单纯 filter 没跑。
- 主要还是匹配质量和 rigid 约束之间不匹配。
